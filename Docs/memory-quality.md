# Качество памяти Iris: извлечение, сохранность и стоимость

Проверено 18–19 октября 2026 года. Изменения относятся к backend из этого checkout;
запущенная или установленная сборка начнёт использовать их после обновления Core.

## Что мешало запоминанию

| Причина | Последствие | Изменение |
| :--- | :--- | :--- |
| `current`/`period` ошибочно означали единственное значение | Новая изучаемая тема, привычка или проект вытесняли предыдущие | Время и количество значений разделены; цели тоже могут быть параллельными |
| TTL у профессии, места проживания, учёбы, проектов и привычек | Молчание пользователя превращалось в исчезновение факта | Автоматически истекает только кратковременное состояние |
| Узкий фильтр запуска и проверка «есть хотя бы одно свидетельство» | Бытовые формулировки и дополнительные сведения после имени пропускались | Содержательное повествование проверяет модель; быстрый путь требует полного покрытия реплики |
| Несогласованные имена полей и неполный словарь | Отклонялись `user.preference`, `user.note`, сведения об устройствах и другие личные факты | Единый словарь, нормализация имён и тип `personal_fact` для прочих явных сведений |
| Хвост из 12 сообщений и равномерное обрезание каждой строки | Терялись старшие реплики и середина длинной фразы, хотя всё окно считалось обработанным | Полный новый диапазон проходит порциями; пользовательский текст не обрезается |
| Поиск совпадений только среди первых 250 фактов | При росте профиля переставали находиться дубликаты и некоторые основные сведения | Прямые запросы по каноническому полю |
| Сортировка по случайному ID перед обрезанием, скрытый лимит 450 | Полезные факты могли не попасть в ответ | Приоритет релевантности, компактного профиля и настроенного бюджета |
| UTC-дата источника на границе местных суток | «Вчера» могло стать неверной календарной датой | В извлечении относительных дат тот же момент показан в местном часовом поясе; SQLite сохраняет исходное время UTC |

В проверенном снимке desktop-базы было 17 активных записей и 21 событие
`autonomous_rejected_unknown_slot`. Это свидетельство конкретного дефекта
совместимости названий, а не оценка полноты памяти во всех разговорах.

## Как принимаются решения

Модель выделяет самостоятельные, понятные вне исходной фразы факты. Повседневное
сведение не обязано иметь исключительную важность: в balanced-режиме для устойчивых
сведений допускается importance от 0.45 при сохранении настроенного порога confidence
(по умолчанию 0.85). Для кратковременного состояния действует исходный порог важности.
Низкая уверенность, неясные социальные связи и чувствительные сведения остаются
основанием для отказа или уточнения. Секреты не сохраняются.

Новая запись о другом проекте дополняет память. Исправление расписания заменяет
именно соответствующую запись: извлекатель видит небольшой список релевантных
известных фактов и может указать `supersedes_id`. Проверяются поле, явность исправления,
защита записи и порядок пользовательских источников. Старые задания и пересекающиеся
окна не должны возвращать исправленные, отклонённые или удалённые факты из тех же
источников. Просьба «не запоминай» исключает реплику из автоматической памяти.

Хранение и контекст разделены. SQLite сохраняет факты; гибридный поиск выбирает
нужные, а ядро профиля добавляет не более двух записей: имя и предпочтение длины
ответов. Старая учёба или цель сохраняется с временем подтверждения; модель получает
указание не выдавать это за новое подтверждение текущего состояния.

Архитектурный ориентир — извлечение, консолидация и выборочный поиск, описанные в
[Mem0](https://arxiv.org/abs/2504.19413), и разделение компактной основной памяти
с архивом в [Letta](https://docs.letta.com/v1-sdk/concepts/stateful-agents).
Показатели чужих бенчмарков к Iris не переносятся. Новый сервис, графовая БД или
отдельная модель классификации для этих исправлений не потребовались.

## Проверки и расход

Пять синтетических сценариев прогнаны через настроенный DeepSeek. Прежний
извлекатель из Git HEAD сравнивался с новым при одной текущей политике хранения.
Это сравнение извлекателей, не полноценное сравнение двух сборок приложения.

| Извлекатель | Сценарии | Входные токены | Выходные токены | Вызовы |
| :--- | ---: | ---: | ---: | ---: |
| Из Git HEAD | 3/5 | 3958 | 807 | 5 |
| Новый, первый прогон | 5/5 | 4550 | 948 | 6 |

Новый вариант сохранил расписание, семейную информацию, устройство, параллельную
учёбу, привычку и важное событие; вымышленная биография не стала памятью.
Общий расход в этом малом прогоне вырос на 15.4%, включая дополнительный вызов
исправления JSON. Это не прогноз месячной стоимости и не гарантия полной памяти.
Полный отчёт: `output/memory-retention-20261018/live-evaluation.json`.

Финальная расширенная проверка: **8/8 сценариев**, 8 вызовов, 7722 входных и
1393 выходных токена. Дополнительно проверены короткие ответы о городе и возрасте,
адресное исправление расписания и календарная дата события после местной полуночи.
Отчёт: `output/memory-retention-20261018/live-final.json`.

Обычная короткая реплика остаётся одним запросом. Большой разговор может стоить
дороже прежнего обрезанного окна: теперь его сведения действительно передаются
извлекателю. Диагностика задания содержит `batch_count`, `batch_request_chars`,
`source_message_count` и суммарную оценку токенов.

Автоматические регрессии покрывают параллельные факты, исправления, старые задания,
сохранность пользовательского текста, сбой поздней порции, согласие на чувствительную
память, запрет сохранения, поиск по словоформам и приоритет фактов в контексте.
Живые тесты не доказывают качество длительного общения или голосового распознавания.

Общий pytest-прогон: **1240 passed, 1 deselected** (hardware-проверка).
После последних доработок прошли целевые прогоны на 61 и 52 теста. Корпус
`evaluate_memory.py` прошёл с precision/recall/retrieval recall = 1.0 на своих
небольших фиксированных примерах. Проверены синтаксис, `git diff --check` и
импорт с записью SQLite в `build/release-venv`. Сводка и полный лог:
`output/memory-retention-20261018/validation-summary.json`, `pytest-final.txt`.

## Существующая база

`repair_v21_memory_retention` выполняется один раз при запуске Core. Она убирает
ошибочные TTL, обновляет канонические поля и может восстановить подтверждённые
источниками потери от прежней политики. Пользовательские удаления, исправления
и отклонения не отменяются. Если исходных сообщений уже нет, сомнительные записи
не активируются автоматически.

На резервном снимке реальной базы после миграции остались все 17 активных записей,
все строки памяти и пользовательские удаления; `PRAGMA integrity_check` вернул `ok`.
Повторный запуск миграции ничего не изменил. Восстановлено 0 старых записей:
исходных сообщений отклонённых предложений в снимке уже нет. Рабочая база этим
испытанием не изменялась. Снимок содержит личные данные и остаётся в игнорируемом
каталоге `output`, вне Git.
